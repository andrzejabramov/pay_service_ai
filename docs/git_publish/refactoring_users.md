# 📄 ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ГОСТ 19.201-78)

**Наименование системы:** Микросервисная платформа учета платежей и пользователей `pay_services`  
**Объект автоматизации:** Модули `auth`, `users` и ядро учета лицевых счетов (`core`)  
**Версия документа:** 1.0  
**Дата:** 17.09.2026

---

## 1. ВВЕДЕНИЕ

Настоящее техническое задание устанавливает требования к разработке (рефакторингу) программных модулей `auth` и `users` в составе монорепозитория `pay_services`. Система предназначена для управления идентификацией пользователей, разграничения ролей (Поставщик, Плательщик, Гость, Менеджер) и обеспечения транзакционного учета средств через иерархию лицевых счетов (Ledger).

## 2. ОСНОВАНИЯ ДЛЯ РАЗРАБОТКИ

1. Договор на разработку ПО № [Указать номер] от [Дата].
2. Протокол анализа требований (метод 3-х цветов) от 17.09.2026.
3. Архитектурный дайджест монорепозитория `pay_services` (версия 1.0).

## 3. НАЗНАЧЕНИЕ РАЗРАБОТКИ

Система обеспечивает:

- Регистрацию, аутентификацию и управление жизненным циклом пользователей.
- Гибкое назначение бизнес-ролей через связь многие-ко-многим (M:N).
- Автоматическую генерацию иерархических номеров лицевых счетов (ЛС) по шаблонам `RR-PPPP-SSSS` (Поставщик) и `RR-PPPP-SSSS#CCCC` (Плательщик).
- Гарантированную транзакционную целостность операций с балансом через хранимые процедуры PostgreSQL.

### 4.2. Требования к надежности

1. **Целостность данных:** Любая операция, изменяющая баланс (`core.base_account.balance`), должна выполняться в рамках одной транзакции БД через вызов SP. Использование ORM для этих операций **запрещено**.
2. **Обработка исключений:** Все ошибки должны маппиться в стандартизированный JSON-ответ через глобальный обработчик FastAPI, используя базовый класс `AppException` (поля: `message`, `status_code`, `error_code`, `details`).
3. **Идемпотентность:** Эндпоинты создания ЛС и регистрации пользователей должны быть идемпотентными (повторный запрос с теми же данными не должен создавать дубликаты).
4. **Время отклика:** Время выполнения хранимых процедур учета не должно превышать 50 мс (p95).

## Приложение Б: Спецификация ключевых API-эндпоинтов (Swagger Draft)

**1. POST `/api/v1/users/` (Регистрация Поставщика/Плательщика)**

- **Request:** `RegisterRequest` (second_login, phone, email, password, role_names)
- **Response:** `UserReadExtended` (id, contacts, groups, **generated_personal_ls**)
- **Logic:** Создает пользователя → создает запись в `user_roles` → вызывает SP `generate_ledger_account` для личного баланса.

**2. POST `/api/v1/users/{user_id}/services/` (Добавление услуги Поставщиком)**

- **Request:** `ServiceCreateRequest` (service_code, region_code)
- **Response:** `LedgerAccountRead` (account_number: `RR-PPPP-SSSS`)
- **Logic:** Проверяет роль Поставщика → вызывает SP генерации сервисного ЛС → создает черновик договора в `contracts`.

**3. POST `/api/v1/ledger/transfer/` (Транзакция между счетами)**

- **Request:** `TransferRequest` (donor_ls, recipient_ls, amount, purpose)
- **Response:** `TransactionRead` (id, status, timestamp)
- **Logic:** Вызывает SP `transfer_funds(donor, recipient, amount)`. Гарантирует атомарность.

## 📎 ПРИЛОЖЕНИЕ Г: Детализация архитектурных решений и пошаговых инструкций по рефакторингу

Данное приложение описывает стандартизированные паттерны взаимодействия компонентов системы и разбивает работу на изолированные «Пакеты доработок». Каждый пакет может выполняться параллельно разными разработчиками, так как зоны ответственности и контракты строго разграничены.

### 1. Стандартный паттерн обработки CRUD-запросов (The Golden Path)

Для всех операций модификации данных (Create, Update, Delete) применяется единый асинхронный паттерн, гарантирующий скорость ответа и надежность уведомлений:

1. **Вход:** HTTP-запрос валидируется через Pydantic-схемы в слое `routers`.
2. **Транзакция БД:** Вызов хранимой процедуры (Stored Procedure) через `asyncpg` (пул `write_pool`). ORM запрещен.
3. **Непосредственный ответ:** Система немедленно возвращает HTTP-ответ (200/201) клиенту с результатом операции.
4. **Кэширование (Redis):** Асинхронное обновление или инвалидация кэша, связанного с измененной сущностью.
5. **Публикация события (RabbitMQ):** Отправка сообщения в очередь для триггера асинхронных действий (отправка SMS/Email, аудит, вебхуки).

---

### 2. Механизмы кэширования (Redis)

- **Инструмент:** Декораторы на базе `fastapi-cache2` (или кастомный wrapper над `aioredis`), интегрированный через FastAPI `Depends`.
- **Стратегия инвалидации:** Явная (Explicit Invalidation). Кэш сбрасывается только при успешном выполнении хранимой процедуры модификации данных.
- **TTL (Time To Live) по умолчанию:**
  - `user_profile_{user_id}`: 300 секунд (5 минут). Инвалидируется при `UserUpdate`.
  - `user_roles_{user_id}`: 600 секунд (10 минут). Инвалидируется при изменении ролей.
  - `ledger_balance_{account_number}`: 60 секунд (1 минута). Инвалидируется после любой транзакции по счету.
  - `service_catalog`: 3600 секунд (1 час). Инвалидируется администратором при добавлении новых услуг.

---

### 3. Асинхронное взаимодействие (RabbitMQ)

- **Архитектура:** Topic Exchange (`notifications_exchange`).
- **Producer (Издатель):** Сервисы `users`, `contracts`, `core`. Публикуют события после успешной записи в БД.
- **Consumer (Потребитель):** Микросервис `notification_service` (или выделенный воркер).
- **Маршрутизация (Routing Keys):**
  - `user.registration.completed` → триггерит Welcome Email.
  - `ledger.account.created` → триггерит SMS с номером нового лицевого счета.
  - `contract.renewal.scheduled` → триггерит Email за 10 дней до окончания договора.
- **Надежность:**
  - Подтверждение доставки (`ack`) только после успешной отправки уведомления внешним шлюзом.
  - При ошибке внешнего шлюза (5xx) сообщение возвращается в очередь с экспоненциальной задержкой (Retry Policy: 1m, 5m, 15m).
  - После 3 неудачных попыток сообщение перемещается в **Dead Letter Queue (DLQ)** (`notifications_dlq`) для ручного разбора администратором.

### 4. Изолированные пакеты доработок (Refactoring Packages)

### 📦 Пакет 1: Ролевая модель (M:N) и Верификация

**Цель:** Переход от жестких групп к гибким бизнес-ролям и внедрение гибридной верификации.

- **Доработки БД:**
  - Создать таблицу `user_roles` (связь M:N между `users` и справочником ролей).
  - Добавить поле `is_verified` и `verified_at` в таблицу `user_contacts`.
  - Написать миграцию для переноса существующих данных из `user_group_memberships` в `user_roles`.
- **Доработки API (`users` service):**
  - _Изменить:_ `POST /api/v1/users/` (Register). На входе: массив `role_names`. На выходе: созданный пользователь + список назначенных ролей.
  - _Добавить:_ `POST /api/v1/users/{id}/contacts/{contact_id}/verify`. Логика: генерация кода → отправка (Email приоритетно, fallback на SMS при ошибке Email) → проверка кода → установка `is_verified=true`.
- **Кэш:** Инвалидация `user_profile_{user_id}` и `user_roles_{user_id}`.
- **Очередь:** Публикация `user.registration.completed` для отправки Welcome-письма.

### 📦 Пакет 2: Генератор Лицевых Счетов (Ledger Core)

**Цель:** Автоматическое создание иерархических номеров счетов при регистрации услуг или привязке клиентов.

- **Доработки БД:**
  - Создать хранимую процедуру `core.generate_ledger_account(p_owner_id UUID, p_type VARCHAR, p_region_code VARCHAR, p_service_code VARCHAR, p_customer_suffix VARCHAR)`.
  - _Логика SP:_ Формирование строки `RR-PPPP-SSSS` (или с суффиксом `#CCCC`). Проверка уникальности через `SELECT ... FOR UPDATE`. Вставка в `core.base_account`. Возврат сгенерированного номера.
- **Доработки API (`users` / `core` service):**
  - _Добавить:_ `POST /api/v1/ledger/accounts`. На входе: параметры генерации. На выходе: объект `LedgerAccountRead` (номер, тип, баланс=0).
  - _Зависимость:_ Требует наличия активной роли «Поставщик» у `owner_id` (проверка через `Depends(require_role(['provider']))`).
- **Кэш:** Инвалидация кэша услуг поставщика.
- **Очередь:** Публикация `ledger.account.created` (payload: `account_number`, `owner_id`) для аудита и логирования.

### 📦 Пакет 3: Маппинг внешних идентификаторов (Банки/ПС)

**Цель:** Централизованное хранение внешних ID для корректной обработки вебхуков от `alpha_hook` и `webhook_2can`.

- **Доработки БД:**
  - Использовать существующую таблицу `common.mappings`.
  - Создать хранимую процедуру `common.upsert_external_mapping(p_internal_id UUID, p_system VARCHAR, p_external_id VARCHAR, p_metadata JSONB)`.
- **Доработки API (`users` service - админский контур):**
  - _Добавить:_ `PUT /api/v1/users/{id}/external-mappings`. На входе: массив объектов `{system: 'ALFA', external_id: '12345'}`. На выходе: обновленный список маппингов.
- **Кэш:** Инвалидация `user_mappings_{internal_id}` (TTL: 3600s).
- **Очередь:** Не требуется (операция административная, не требует мгновенных уведомлений).

### 📦 Пакет 4: Автопролонгация договоров и Уведомления

**Цель:** Автоматическое продление договоров и информирование сторон.

- **Доработки БД:**
  - Добавить в `contracts` поля: `auto_renew` (boolean), `renewal_period_days` (int, default 365).
  - Создать хранимую процедуру `contracts.extend_contract(p_contract_id UUID, p_days INT)`.
- **Доработки API / Фоновые задачи:**
  - _Добавить:_ Celery Beat задачу (или RabbitMQ Delayed Message), которая ежедневно выполняет запрос: `SELECT id FROM contracts WHERE valid_to = CURRENT_DATE + 10 AND auto_renew = true`.
- **Очередь (Двухэтапная):**
  1.  **Producer (Cron):** Публикует `contract.renewal.scheduled` (payload: `contract_id`, `user_email`).
  2.  **Consumer (Notification):** Отправляет Email. Если в течение 10 дней не поступило события `contract.cancellation.requested`, тот же Consumer (или отдельный cron) публикует `contract.renewal.executed`.
  3.  **Consumer (Contracts):** Слушает `contract.renewal.executed` и вызывает SP `extend_contract`.

### 5. Контракты внешних интеграций (Notification Service)

Для обеспечения единого стандарта, все внутренние сервисы общаются с модулем уведомлений через строго типизированные JSON-сообщения в RabbitMQ или через внутренний HTTP API.

### Внутренний API Notification Service (для синхронных вызовов, если нужны)

- **Endpoint:** `POST /internal/v1/notifications/send`
- **Request Body:**
  ```json
  {
    "user_id": "uuid-string",
    "channel": "email", // или "sms"
    "template_code": "CONTRACT_RENEWAL_10_DAYS",
    "variables": {
      "contract_number": "Д-123/2026",
      "expiry_date": "2027-09-17"
    }
  }
  ```
- **Response Body:**
  ```json
  {
    "message_id": "msg-uuid",
    "status": "queued" // или "sent", "failed"
  }
  ```

### Формат сообщения в RabbitMQ (для асинхронных вызовов)

- **Exchange:** `notifications_exchange`
- **Routing Key:** `notification.request`
- **Payload:** Аналогичен Request Body выше, плюс поле `retry_count: 0`.

### 6. Инструкция по параллельной разработке (для команды / AI-агентов)

Чтобы исключить конфликты слияния (merge conflicts) и блокировки, разработка распределяется следующим образом:

1.  **Разработчик А (DB & Core):** Реализует **Пакет 2** (SP генерации счетов) и **Пакет 3** (SP маппингов). Работает исключительно в папке `sql/schemas/`.
2.  **Разработчик Б (Auth & Users API):** Реализует **Пакет 1** (роли, верификация) и обновляет Pydantic-схемы. Интегрирует вызов SP из Пакета 2 через `asyncpg`.
3.  **Разработчик В (Infrastructure & Async):** Настраивает **Пакет 4** (RabbitMQ продюсеры/консюмеры, Celery Beat) и реализует логику инвалидации Redis (`fastapi-cache2`) во всех новых эндпоинтах.

_Примечание:_ Интеграция между пакетами происходит строго через опубликованные контракты (имена хранимых процедур, названия полей Pydantic, routing keys RabbitMQ), которые зафиксированы в данном документе.

---

Этот формат дает разработчику (или AI-агенту типа Cline) четкий чек-лист: «Вот таблица, которую надо изменить. Вот хранимая процедура, которую надо вызвать. Вот ключ, под которым надо сбросить кэш. Вот сообщение, которое надо кинуть в очередь». Никакой двусмысленности, чистая инженерная спецификация.
